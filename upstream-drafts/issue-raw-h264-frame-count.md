# `mouselite run` silently writes empty results when the container frame count is wrong (e.g. raw .h264)

---

## What happens

When the video's container reports a wrong frame count, `mouselite run` stops early or reads nothing, and still exits 0 with `wrote <path>`.

- **No count at all:** a raw H.264 elementary stream (`.h264`, no container) reports a garbage `CAP_PROP_FRAME_COUNT`. The run writes **0 images** to `_annotations.json` and header-only CSVs, and stores the bogus `total_frames` in `info`.
- **Count too low:** a container whose count is below the number of decodable frames is silently truncated at the reported count.

Users recording from camera pipelines (Raspberry Pi, `rpicam`, GStreamer) often have raw `.h264` chunks, so the run "succeeds" with no data.

## Reproduce

Tested with mouselite v0.1.3, opencv-python 5.0.0.93 (FFMPEG backend), supervision 0.30.0, on Linux.

```bash
ffmpeg -f lavfi -i testsrc=size=320x240:rate=25 -t 2 -c:v libx264 -pix_fmt yuv420p -f h264 raw.h264
```

```python
import cv2, supervision as sv

cap = cv2.VideoCapture("raw.h264")
print(cap.get(cv2.CAP_PROP_FRAME_COUNT))      # -192153584101141
n = 0
while cap.read()[0]:
    n += 1
print(n)                                      # 50: OpenCV decodes every frame

print(sum(1 for _ in sv.get_video_frames_generator("raw.h264")))  # 0
```

Running `Pipeline.run("raw.h264", ...)` with the test suite's `FakeKeypointModel` gives `images: []`, an empty `_trajectories.csv`, and `"total_frames": -192153584101141` in `info`.

## Cause

`Pipeline.run` reads frames with `sv.get_video_frames_generator` (`src/mouselite/pipeline.py:229`). supervision sets the end of the read to the container's `CAP_PROP_FRAME_COUNT` and stops at `frame_position >= end` (`supervision/utils/video.py:176-183, 296-298` in 0.30.0). With a negative count the loop ends before the first frame; with a low count it ends early. `retrack` reads the same way (`src/mouselite/tracker.py:99`).

## Possible fixes (maintainer's choice)

1. **In MouseLite:** read with a plain `cv2.VideoCapture` loop until `read()` fails, and use the container count only for the progress bar (or none when it is ≤ 0).
2. **Guard:** at minimum, raise when the count is ≤ 0 or when no frame was decoded, instead of writing empty results.
3. **Upstream:** report to supervision that `get_video_frames_generator(end=None)` should read to end of stream rather than to the container count.

Related, smaller: `info.fps` and the CSV `time` column come from the container's fps, which a raw stream doesn't carry reliably. An `--fps` override would help such inputs. For now, remuxing with an explicit rate (`ffmpeg -framerate 15 -i chunk.h264 -c copy chunk.mp4`) works around both problems.

Happy to send a PR for option 1 or 2 if you say which you prefer.
